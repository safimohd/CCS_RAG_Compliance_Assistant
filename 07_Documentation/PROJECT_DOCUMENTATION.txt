--------------------------------------------------------------------------------
2.1 Corpus Assembly
--------------------------------------------------------------------------------

The first major task was gathering source documents. We settled on two domains:
Healthcare and Real Estate (specifically Karnataka RERA).

For Healthcare, documents were organized into authority buckets:
  01_Core_Regulatory        -- Clinical Establishments Act, NMC regulations,
                               PM-JAY instruments. Assigned Tier A (binding).
  02_Core_PMJAY_Insurance   -- PM-JAY insurance framework. Tier A.
  03_Medical_Regulation_    -- NMC regulations and medical education standards.
     Education                 Tier B.
  04_Supporting_Guidance    -- Guidelines, FAQs, manuals, SOPs. Tier C.
  05_Draft_Proposed         -- Draft documents not yet in force. Tier D.
  06_Review                 -- Documents where binding status was unverified.
                               Tier E.

For RERA, the same tier structure applied:
  01_Central_RERA           -- Real Estate (Regulation and Development) Act
                               2016, central rules. Tier A.
  02_Karnataka_RERA         -- Karnataka RERA Rules 2017, K-RERA circulars,
                               penalty notifications, circulars. Tier A.
  03_Supporting_Guidance    -- Guidelines, FAQs. Tier C.

What we discovered that nobody anticipated: 88 of the 350 corpus PDFs had no
text layer at all. They were scanned images. For RERA specifically, roughly
87% of the Karnataka documents were image-only. This meant that without OCR,
retrieval would have silently returned nothing on most RERA queries and we
would never have known why.

PIVOT 1: We ran Tesseract OCR on every image-only PDF. The sidecar text files
live in 02_Corpus/_ocr_text/. ingest_corpus.py checks for these sidecars and
uses them when the PDF yields fewer than 300 characters of extracted text.

Final corpus: 803 PDFs reconciled, producing 345 indexed documents with 25,955
chunks. Healthcare: 24,586 chunks, 258 documents. RERA: 1,369 chunks, 86
documents.

One Kannada-language tier-A document could not be processed (transfer failure).
It is documented as a known accepted loss.

--------------------------------------------------------------------------------
2.2 Embedding and Indexing
--------------------------------------------------------------------------------

We used the BAAI/bge-small-en-v1.5 embedding model (384 dimensions) with
normalize_embeddings=True. This matches what the cohort's benchmark group was
using, so comparisons would be fair.

Chunking: RecursiveCharacterTextSplitter, chunk size 1000, overlap 150.

The index is built by ingest_corpus.py and stored at 05_App/chroma_db/. The
collection is called "regulatory_corpus". Each chunk carries metadata for
domain (Healthcare or RERA), authority tier (A through E), and document title.

One critical decision: ingest_corpus.py's main() calls clear_index() at the
very top, before the 35-minute extraction process begins. This was not how it
was originally written. It was moved after a painful incident where
shutil.rmtree hit a Windows PermissionError (OneDrive lock) partway through
deletion, leaving an index that was present on disk but silently unusable. The
35-minute extraction had already run and was wasted. The fix: delete first,
then extract, so if the delete fails you know immediately and lose no work.

The corpus has an important exclusion: 01_Benchmarks/ is explicitly forbidden
from indexing. If the benchmark's expected answers were in the index, the RAG
system would retrieve its own answer key and invalidate the entire base-vs-RAG
comparison.

Authority tiers and their retrieval weights:
  A: 1.00  (binding regulation -- citable as law)
  B: 0.95  (sector regulation -- binding within sector)
  C: 0.80  (supporting guidance -- explanatory, not binding law)
  D: 0.55  (draft / proposed -- never present as binding)
  E: 0.35  (review -- binding status unverified)

By default, tiers D and E are excluded from retrieval. This cuts the candidate
pool: 38% of Healthcare chunks and 29% of RERA chunks are in excluded tiers.
This turns out to matter a lot (see the benchmark results section).

The index is too large to commit to GitHub (Chroma's sqlite3 file grows past
100MB). It is packaged as chroma_db.tar.gz and uploaded as a GitHub Release
asset (release tag: index-v1). The deployed Streamlit apps download it on
first boot via an INDEX_URL secret.

--------------------------------------------------------------------------------
2.3 Retrieval Pipeline (rag_query.py)
--------------------------------------------------------------------------------

rag_query.py is the core retrieval module. Its retrieve() function handles
everything from embedding the query to returning ranked source chunks.

Key design decisions:

TOP_K = 6 (how many chunks reach the LLM)
CANDIDATE_K = 24 (how many chunks are fetched from ChromaDB before re-ranking)

The 24-candidate approach exists because authority tier weighting happens after
retrieval. A tier-A chunk with a cosine similarity of 0.42 should beat a tier-C
chunk with 0.48. If we just took the top 6 by cosine, authority would not
factor in at all.

Re-ranking formula:
  weighted_score = cosine_similarity * tier_weight

There is a gotcha here that cost us time: ChromaDB's default distance metric
is L2 (Euclidean), not cosine. LangChain reports L2 scores as (1 - L2/sqrt(2)),
which goes negative for distant vectors. The function to_cosine() in rag_query.py
corrects this using the fact that for unit-normalized vectors:
  cosine = 1 - (1 - score)^2

This matters because if you sort by raw (possibly negative) cosine and multiply
by tier weight, a tier-A chunk at cosine -0.30 scores (-0.30 * 1.00 = -0.30)
while a tier-C chunk at cosine -0.30 scores (-0.30 * 0.80 = -0.24). The tier-C
chunk sorts higher. Authority inverts precisely when retrieval is weakest and
matters most. Both the L2-to-cosine conversion and the non-negative relevance
formula are fixed in rag_query.py.

The system prompt instructs the LLM to cite tier and document title for each
claim, state when material is from guidance rather than binding law, and decline
to speculate beyond what the documents say.

Maximum 2 chunks per source document is enforced to prevent one template
document from flooding the context window. This created a problem (see
benchmark results).

--------------------------------------------------------------------------------
2.4 The Two Discovery Bugs (September 2026)
--------------------------------------------------------------------------------

BUG 1: Sidecar collision.
Two Karnataka RERA tier-A circulars were character-identical apart from the
financial year. Their sidecar OCR files got swapped during the ingestion run.
This meant document A served document B's penalty figures under the correct
title and correct authority tag. The system gave confident, authoritative,
wrong answers. Fixed in September by renaming the sidecar files correctly and
rebuilding the index.

BUG 2: Scope filter was post-filtering instead of pre-filtering.
The original scope filter worked like this: retrieve 24 chunks from ChromaDB,
then remove any chunks whose document title did not match the user's selection.
If nothing matched, fall back to the unscoped 24 chunks.

The problem: a physiotherapy equipment question returned a Yoga standards DRAFT.
Not because the Yoga draft was more relevant, but because roughly 20 near-identical
CEA (Clinical Establishments Act) facility templates, one per facility type, were
filling all 24 candidate slots. The physiotherapy document existed in the index
but never made it into the top 24 chunks. The post-filter found nothing matching
"physiotherapy" and fell back to returning the first chunk it had, which was the
Yoga draft.

PIVOT 2: Move all filters inside the ChromaDB where clause, not after retrieval.
The correct architecture: domain, tier, and scope filters all go into the Chroma
query's where parameter before any chunks are fetched. This was the core change
in October 2026.

After fixing this, tier starvation was also discovered: a query that should
return healthcare staffing requirements was returning zero documents, because
the 24-chunk candidate window was being filled by excluded-tier chunks (drafts
and review documents) which then all got filtered out. Zero chunks meant no
answer. Moving the tier filter inside the where clause fixed this too.

--------------------------------------------------------------------------------
2.5 Two Mis-Tiered Drafts (October 11, 2026)
--------------------------------------------------------------------------------

During testing, Yoga Standards and Siddha Standards documents were showing up
in answers alongside binding law. These two documents said DRAFT in their titles.
Ten other draft documents were correctly tiered D and excluded. These two were
tiered C (supporting guidance, included by default).

fix_draft_tiers.py was written to re-tier them: C to D in both the ChromaDB
collection (194 chunks updated) and in 03_Metadata/ingestion_report.csv (2 rows
corrected). After this, they were excluded from default retrieval.

--------------------------------------------------------------------------------
2.6 Scope Design: What "Filtering" Actually Means
--------------------------------------------------------------------------------

Three designs were tried and two were rejected:

Design 1: Post-filter with fallback.
  Retrieve 24 chunks, then filter by title. If nothing matches, return
  the unscoped results. This is the silent-widening bug. Rejected.

Design 2: Strict title allowlist.
  Filter to only the exact selected documents. This hid 90% of Healthcare and
  75% of RERA documents for most queries. A scope filter of "FY 2023-24" would
  miss Section 4(2)(l)(D) of the RERA Act and the 2020 bank account directions
  because neither carries a year in its title. Rejected.

Design 3 (shipped): Exclude competing narrow documents, keep general law.
  The insight: only 17 of 161 retrievable Healthcare documents are tied to a
  specific facility type. Only 13 of 53 RERA documents are tied to a specific
  financial year. The general law is the large majority. So the rule is:
  exclude documents tied to a DIFFERENT narrow category, keep everything else.

  This required FACILITY_MARKERS in rag_query.py: a list of facility type
  strings (including AYUSH types like Yoga and Siddha that have no dropdown
  option but have specific documents) so that "general" does not accidentally
  include a facility-specific draft.

A regression test (measure_scope.py) and an offline test suite (test_scope.py,
7 sections) were written to prevent either rejected design from being
reintroduced. Section 6 of test_scope.py explicitly asserts that the rejected
silent-widening design fails.

--------------------------------------------------------------------------------
2.7 Document Title Cleanup (October 11, 2026)
--------------------------------------------------------------------------------

68 of 214 displayed document titles contained noise that a reviewer should not
see: file sizes ("Hospital (Level 2) (832.09 KB)"), OCR pipe fragments
("1 | OPERATIONAL | GUIDELINES FOR |"), leading numerals, and gazette
registration numbers as the full title.

clean_title() was added to app.py to handle display-only cleanup. The raw title
string is preserved for retrieval and scope matching. What users see in the
source citations is the cleaned version.

--------------------------------------------------------------------------------
2.8 Deployment Architecture
--------------------------------------------------------------------------------

The original plan (August 24) was to deploy to Vercel.

PIVOT 3: We switched to Streamlit Community Cloud.
Reason: The app uses ChromaDB (requires SQLite 3.35+) and the BGE embedding
model, both of which need a persistent runtime environment and disk access.
Vercel is a serverless platform that cannot hold the index between requests.
Streamlit Community Cloud gives each deployment a persistent container.

Two apps, one codebase:
  05_App/app_healthcare.py -- entry point for the Healthcare deployment
  05_App/app_rera.py       -- entry point for the RERA deployment

Each entry file sets APP_DOMAIN before running app.py. The domain selector is
hidden when APP_DOMAIN is set, so a healthcare reviewer cannot see the RERA
interface and vice versa.

Both apps must be public (not private). Private apps cannot be kept warm by
anonymous HTTP pings, because anonymous requests hit a Google sign-in page
rather than the app. Making them public means the daily question limit
(DAILY_QUESTION_LIMIT = 100) becomes the spend control instead.

The pysqlite3 shim: Streamlit Community Cloud ships an older system sqlite3.
ChromaDB requires 3.35+. The shim (pysqlite3-binary) is imported at the top
of app.py before anything imports chromadb, replacing the system sqlite3 in
sys.modules. This fails silently on Windows (where system sqlite3 is new
enough), so it is wrapped in a try/except.

Streamlit Secrets (not hardcoded):
  OPENAI_API_KEY
  INDEX_URL (pointing to the GitHub Release asset)
  LLM_REASONING_EFFORT ("low" -- see below)
  DAILY_QUESTION_LIMIT ("100")
  CONTACT_EMAIL

LLM_REASONING_EFFORT was set to "low" deliberately. Testing showed that lower
reasoning effort cut latency from 60 seconds to 30 seconds AND improved the
FY2023-24 answer. Less reasoning meant less gap-filling from training data.

The index is shipped as a GitHub Release asset (index-v1/chroma_db.tar.gz).
The app downloads and extracts it on first boot. The .gitignore excludes
chroma_db/ and *.tar.gz.

Apps sleep after 12 hours of inactivity. Waking one downloads the ~150MB
index and pulls the BGE model before answering, which takes a few minutes.
keep-warm.yml pings both apps every 10 minutes to prevent sleep.

--------------------------------------------------------------------------------
2.9 Answer Cache and Daily Cap
--------------------------------------------------------------------------------

app.py maintains a local .answer_cache.json (gitignored). Every question hash
is stored with its answer. If the same question is asked again, the cached
answer is returned without calling the LLM API. This is important because the
OpenAI key belongs to Prof. Majumdar, not to us. Retrieval is free (local);
generation is the only API spend.

The daily cap is tracked in .usage.json (also gitignored). It resets at
midnight IST.

PART 3: THE BENCHMARK (October 2026)

--------------------------------------------------------------------------------
3.1 Three-System Design
--------------------------------------------------------------------------------

The benchmark compares three systems on the same questions:

System A: Base LLM
  GPT-5-nano with no retrieval and no domain-specific system prompt.
  This is the baseline: what does the model know from training alone?

System B: Plain RAG
  GPT-5-nano + ChromaDB vector retrieval (rag_query.py).
  This is our standard pipeline.

System C: Agentic RAG
  GPT-5-nano + query decomposition + multi-hop retrieval (agentic_rag.py).
  Complex queries are split into sub-queries. Each sub-query gets its own
  retrieval pass. Results are synthesized before answering. A reflection
  loop reformulates and re-retrieves if the first pass flags insufficient
  evidence.

Questions: 100 per domain (Healthcare and RERA), 200 total.
Tiers 1-5 representing question complexity, with Tier 5 being the most complex
multi-hop queries.

--------------------------------------------------------------------------------
3.2 Scripts and Their Output
--------------------------------------------------------------------------------

05_App/benchmark/run_benchmark.py
  Generates answers from all three systems for every question.
  Output: benchmark/results/benchmark_answers_{timestamp}.xlsx
  Columns: question_id, domain, tier, question_text, expected_answer,
           system_a_answer, system_b_answer, system_c_answer,
           system_c_sub_queries, system_c_steps

05_App/benchmark/evaluate_benchmark.py
  LLM-as-judge scoring. The judge model is Qwen3-8B-Flash on Together AI.
  Rubric (8 points total, specified by Prof. Majumdar):
    Factual Accuracy:       0-4
    Completeness:           0-2
    Confidence Calibration: 0-2
    Total:                  0-8
  Output: benchmark/results/benchmark_evaluation_{timestamp}.xlsx
    Sheet "Scores"      -- one row per (question_id, system)
    Sheet "Summary"     -- averages per domain/tier/system
    Sheet "Comparison"  -- head-to-head table

05_App/benchmark/agentic_rag.py
  System C implementation. Decomposition prompt asks the LLM to split queries
  into focused sub-queries as a JSON array. Each sub-query runs through retrieve().
  Reflection loop triggers if the LLM's answer contains phrases like "insufficient
  evidence" or "cannot determine."

05_App/benchmark/questions_rera.py
05_App/benchmark/questions_healthcare.py
  Question sets for each domain (100 per domain, 5 tiers each).

05_App/benchmark/export_questions.py
  Exports questions to Excel for sharing with other groups.

05_App/benchmark/rerun_missing_answers.py
  Reruns specific rows that failed (by row ID) without redoing the whole benchmark.
  Used for resuming after credit exhaustion.

--------------------------------------------------------------------------------
3.3 Results (October 28, 2026)
--------------------------------------------------------------------------------

The evaluation ran 600 benchmark rows (200 per system). 542 valid rows scored.

Final scores:
  System A (Base LLM, no retrieval): 5.07 / 8
  System C (Agentic RAG):            4.19 / 8
  System B (Plain RAG):              4.04 / 8

The base LLM beat both RAG systems. This is a significant finding.

Why the RAG systems underperformed (diagnosed after the results):

1. Retrieval precision: The embedding model was not consistently ranking the
   correct chunk in the top 24 candidates. If the right chunk misses the top 24,
   it never reaches the LLM. The base model bypasses this entirely.

2. Aggressive tier filtering: 38% of Healthcare chunks and 29% of RERA chunks
   are excluded by default (tiers D and E). This shrinks the effective candidate
   pool significantly, and the right chunk may be in an excluded-tier document.

3. Per-document cap: Maximum 2 chunks per source document. For long authoritative
   sources (like the RERA Act itself), this cuts off useful passages.

The base LLM draws on training knowledge of well-known frameworks like the RERA
Act and the Clinical Establishments Act. These are major legislation that would
appear many times in its training data.

The suggested improvement path from this analysis: better retrieval (hybrid
BM25 + vector search, or a stronger re-ranker) rather than more agentic steps.
Adding more agentic complexity (System C) did not help because the fundamental
problem is retrieval precision, not reasoning.

--------------------------------------------------------------------------------
4.2 K-RERA Project Scraper (scrape_krera.py -> rera_projects)
--------------------------------------------------------------------------------

The K-RERA portal (rera.karnataka.gov.in) lists all registered real estate
projects in Karnataka. The scraper hits the portal's project detail pages and
enriches each row in rera_projects with:
  status, district, taluk, project_type, total_units, sold_units,
  completion_date, reg_date, lapse_date, land_area_sqft, detail_url

The table has 10,096 rows. The enrichment column is enriched_at (NULL means
not yet enriched). The scraper queries WHERE enriched_at IS NULL and processes
rows in batches of 50, writing back via Supabase REST upsert with
Prefer: return=minimal.

GitHub Actions workflow: .github/workflows/scrape.yml
  Trigger: workflow_dispatch only (manual)
  Timeout: 300 minutes (5 hours)
  Inputs: limit (default 0 = all), dry_run, re_enrich_days

What went wrong:
  Run #4 was cancelled after exactly 5 hours 0 minutes 55 seconds. The reason:
  limit=0 tried to enrich all 10,096 rows at once. At approximately 1.5 seconds
  per row (network round-trip to the K-RERA portal), that is roughly 15,000
  seconds = 4.2 hours of actual work plus overhead. GitHub's 6-hour cap was hit.
  Additionally, no ntfy notification was wired up, so we got no alert that the
  run was cancelled.

  Also discovered: the enriched column does not exist. The correct column is
  enriched_at. An earlier script version used WHERE enriched = false which
  silently returned all rows.

Fixes applied:
  1. Added ntfy notification block to scrape.yml with 3 states:
     success (white_check_mark), cancelled (warning), failed (x).
  2. Recommended batch size going forward: --limit 1000 per run, spread over
     several days.
  3. Correct query: WHERE enriched_at IS NULL

--------------------------------------------------------------------------------
4.6 Price Estimator (estimate_2026_prices.py -> property_prices_estimated)
--------------------------------------------------------------------------------

Bridges the gap between the 17 NoBroker localities (2026 prices) and the 1,300+
Kaggle localities (2017 prices).

The algorithm:
  Step 1: For each locality, compute the Kaggle 2017 median price per sqft.
  Step 2: For the 17 localities where NoBroker has a 2026 price and Kaggle
          has 2017 data: scaling_factor = NoBroker_2026 / Kaggle_2017_median
  Step 3: Assign every locality to a Bangalore zone:
          North, South, East, West, Central, Peripheral
  Step 4: For each zone, average the scaling factors of localities where both
          sources exist. This is the zone scaling factor.
  Step 5: For localities without a direct NoBroker 2026 price, apply the
          zone scaling factor to their Kaggle 2017 median.

Output: 1,292 rows, one per locality, with:
  estimated_ppsf_2026, ppsf_min_2026, ppsf_max_2026,
  source_ppsf_2017, scaling_factor, scaling_method, listing_count_2017

GitHub Actions workflow: .github/workflows/estimate_2026_prices.yml
  Trigger: workflow_dispatch only (manual)
  Timeout: 20 minutes
  Inputs: dry_run

--------------------------------------------------------------------------------
4.7 Pincode Scraper (scrape_pincodes.py -> pincodes)
--------------------------------------------------------------------------------

Fetches Karnataka pincode data from the free India Post API
(api.postalpincode.in). The Karnataka pincode range is 560001 to 591346.
The script iterates through every pincode in the range, calling the API once
per pincode with a 0.3-second delay (polite rate limiting).

For each valid Karnataka post office, it stores:
  pincode, office_name, delivery_status, district, division_name,
  region, block, state, country, fetched_at

Batch size: 200 rows per Supabase upsert.

GitHub Actions workflow: .github/workflows/scrape_pincodes.yml
  Trigger: workflow_dispatch only (manual)

What went wrong:
  Run #2 showed as successful after 4 hours 36 minutes. But the pincodes table
  had 0 rows. 4.5 hours of work, completely wasted.

  Root cause: Missing UNIQUE constraint on (pincode, office_name). The script
  uses Supabase's merge-duplicates upsert (Prefer: resolution=merge-duplicates).
  This upsert mode works by finding existing rows that match on the unique key
  and either updating them (if found) or inserting (if not). Without a unique
  constraint, Supabase has no key to merge on. It silently writes 0 rows and
  returns HTTP 200. No error. No warning. The workflow reported success.

Fix applied: SQL migration run via Supabase MCP tool:
  ALTER TABLE pincodes ADD CONSTRAINT pincodes_pincode_office_unique
  UNIQUE (pincode, office_name);

The pincode scraper needs to be re-run from scratch after this fix.
Estimated runtime: 4.5 hours (full Karnataka range).

PART 5: GITHUB ACTIONS WORKFLOWS

PART 11: KNOWN GOTCHAS (do not relearn these)
================================================================================

1. ingest_corpus.py's clear_index() runs at the TOP of main(), before extraction.
   Do not move it. See Part 2.2 for why.

2. L2 vs cosine score inversion. ChromaDB defaults to L2. LangChain reports
   1 - L2/sqrt(2), which goes negative. to_cosine() in rag_query.py corrects
   this. Never rank by raw score from ChromaDB. See Part 2.3.

3. Supabase merge-duplicates upsert requires a UNIQUE constraint. Without one,
   the upsert writes 0 rows and returns HTTP 200 with no error. This destroyed
   4.5 hours of work on the pincodes scraper. See Part 4.7.

4. WHERE enriched = false does not work. The column is enriched_at. Use
   WHERE enriched_at IS NULL.

5. GitHub Actions 6-hour cap. Any workflow that might run for more than 6 hours
   will be cancelled. Use smaller --limit values and batch over multiple runs.
   Always wire ntfy notifications so you know when a run is cancelled.

6. Streamlit Community Cloud's SQLite is old. The pysqlite3 shim must be
   imported before chromadb. It is at the top of app.py. If it moves, the app
   will fail to start on Community Cloud.

7. The index (chroma_db/) must not be committed. It exceeds GitHub's 100MB
   file limit. It lives in the GitHub Release (index-v1). The .gitignore
   covers chroma_db/ and *.tar.gz.

8. Never commit .env. It contains API keys. The .gitignore covers it. All
   secrets go through st.secrets (deployed) or environment variables (local).

9. The OpenAI key (GPT-5-nano) belongs to Prof. Majumdar. It is not ours.
   Every API call costs money from his account. The answer cache (Part 2.9)
   and the daily question limit exist for this reason.

10. huggingface.co is blocked by the Claude container's egress proxy. The BGE
    embedding model cannot be downloaded in a Claude session. Indexing must
    run on the user's own machine. Reading ChromaDB metadata (titles, tiers)
    can be done in a Claude session by staging chroma.sqlite3 and querying it
    with plain SQL (no model needed).

11. BankBazaar/Yahoo Finance rate-limits scrapers. Do not run scrape_market_rates
    twice within a few minutes. Wait at least an hour between runs.

12. The Yoga and Siddha draft documents were mis-tiered C instead of D.
    fix_draft_tiers.py has already been applied. Do not re-run it. The index
    has already been updated. If the Release asset has not been replaced after
    this fix, the deployed app still uses the old tiers.

  regulatory text well, but real estate professionals already know the
  regulations. The tool needs a sharper definition of who it is actually built
  for."

SPECIFIC FEEDBACK POINTS:

1. Target Audience
   The primary gap: the tool lacks a clearly defined target user. Real estate
   agents, lawyers, and developers have enough domain knowledge to navigate RERA
   themselves. The more valuable user is someone who does not have that
   background and is making a high-stakes decision without expert support. The
   tool should be rebuilt around that person.

   Action: Define the target audience precisely before the next demo.

2. PDF Upload and Document Q&A
   Strong suggestion to add the ability for users to upload their own documents
   (sale deeds, builder agreements, brochures) and ask questions against them
   in combination with the RERA corpus. This is the feature that would
   differentiate the tool from a simple portal search, since it works on the
   user's specific situation rather than general regulations.

   Action: Build PDF upload and document Q&A as the highest-priority feature.
   (Note: Prof. Majumdar's Nov 3 feedback also pointed toward PDF upload. Both
   professors independently converged on this as the most important gap.)

3. Investment Signals and Area-Level Guidance
   The tool should help users understand whether a particular area, pin code,
   or builder has a track record worth trusting. Surfacing complaint patterns,
   project delay history, and registration status at a geographic level would
   add genuine decision-making value.

   Action: Add Karnataka RERA project lookup by name and pin code, and add an
   investment signal view for area-level context. The pincodes table (Part 9)
   and rera_projects table support this once populated.

4. Building and Society Name Lookup
   Users frequently come with a specific project in mind. The tool should allow
   lookup by building name or society name to surface compliance status,
   complaints filed, completion timelines, and any RERA violations.

   Action: Wire the rera_projects table into a project search interface.

5. Predictive Regulation Model (long-term)
   A longer-term suggestion: forecast which regulations are likely to be amended
   or enforced more strictly, based on complaint trends and policy signals. This
   would shift the tool from reactive (what does the law say?) to proactive
   (what is the law likely to become?).

   Action: Consider as a future research angle, not an immediate build.

PRIORITY ORDER SET BY PROF. DEB:
  - Define the target audience precisely before the next demo
  - Build PDF upload and document Q&A as the highest-priority feature
  - Add Karnataka RERA project lookup by name and pin code
  - Add an investment signal view for area-level context
  - Consider predictive regulation as a longer-term research angle

PART 15: BENCHMARK -- ORIGINAL 4-CONDITION DESIGN AND PIVOT
================================================================================

THE ORIGINAL PLAN (before Together AI blocked us):

The benchmark was originally designed with 4 conditions, all using the same
question set:

  Condition 1: RAG (gpt-5-nano + our ChromaDB retrieval)
  Condition 2: Base LLM (gpt-5-nano, no retrieval -- same model, no context)
  Condition 3: Larger open-source LLM (openai/gpt-oss-20b on Together AI)
  Condition 4: Smaller open-source LLM (google/gemma-3n-E4B-it on Together AI)

The intent was to isolate what retrieval adds (Condition 1 vs 2) and also test
whether model size matters (Condition 3 vs 4) independently of retrieval.

WHAT HAPPENED:
  The Together AI API key provided by Prof. Majumdar returned HTTP 401
  (Unauthorized). Both Condition 3 and Condition 4 were blocked. We spent
  significant time assuming the key was correct before diagnosing the issue.
  The key was invalid, not expired -- the account either needed a top-up or
  the privacy setting at api.together.ai/settings/privacy was blocking API
  access.

PIVOT TO 3-SYSTEM DESIGN:
  We restructured the benchmark as three systems rather than four conditions:
    System A: Base LLM -- gpt-5-nano with no retrieval (parametric knowledge only)
    System B: Standard RAG -- top-k=6 chunks from ChromaDB passed to gpt-5-nano
    System C: Agentic RAG -- breaks each question into sub-queries, retrieves
              separately for each, synthesises into one answer (see agentic_rag.py)

  All three use gpt-5-nano. The comparison isolates retrieval strategy, not
  model capability.

PART 17: ADDITIONAL GOTCHAS (supplement to Part 11)
================================================================================

13. run_awake.ps1 -- PowerShell Int32 overflow.
    The script keeps the Windows laptop awake during long jobs (K-RERA scraper,
    benchmark run, evaluation) using Windows SetThreadExecutionState.
    Usage: powershell -ExecutionPolicy Bypass -File ..\run_awake.ps1 "python run_evaluation.py"
    Quotes around the command are required.
    BUG: 0x80000001 (ES_CONTINUOUS | ES_SYSTEM_REQUIRED) is parsed by PowerShell
    as a signed Int32, which overflows. Fix: use [uint32]2147483649 instead of
    0x80000001. The script on disk already has this fix applied.

14. Windows Security blocking scikit-learn .pyd file.
    Windows Defender or Windows Security may quarantine:
    _expected_mutual_info_fast.cp312-win_amd64.pyd
    This file belongs to scikit-learn, which is pulled in by sentence-transformers.
    Symptom: ImportError on sentence_transformers even after pip install.
    Fix: reinstall scikit-learn (pip install --force-reinstall scikit-learn).
    Do not disable Windows Security. The file is a false positive but reinstalling
    is safer than adding exclusions.

15. .usage.json is NOT in .gitignore (suspected).
    The security rules (Part 12) state it should never be committed, but the
    actual .gitignore file may not list it. Verify the .gitignore contains
    .usage.json. If not, add it -- this file holds per-deployment runtime state
    and should not be in source control.

16. keep-warm.yml exists in Part 5 script inventory but has NOT been created.
    GitHub blocks writing to .github/workflows/ from remote sessions (Actions
    API does not support it). The file must be created manually in the repo.
    When created, it should ping both Streamlit app URLs every 10 minutes using
    workflow_dispatch trigger (not cron, per security rules) OR a minimal cron
    if the monitoring use case justifies the exception -- same as daily_report.yml.

17. Empty "Real Estate" folder in project root.
    There is a file-locked folder called "Real Estate" in the project root. It
    appears empty but cannot be deleted due to Windows file locking (possibly
    OneDrive or an open handle). It is cosmetic. Do not spend time on it.

18. The pincodes table has 0 rows (as of Nov 2026) despite a successful-looking
    scraper run. The root cause was a missing UNIQUE constraint on (pincode,
    office_name) -- Supabase's merge-duplicates upsert silently writes 0 rows
    when no UNIQUE constraint exists, returning HTTP 200. The constraint has
    been added via SQL migration. A full re-run of scrape_pincodes.py (GitHub
    Actions scrape_pincodes.yml, no --limit) is required. Estimated 4.5 hours.
    See Part 11, gotcha #3 for the general principle.

19. Sidecar collision bug (RESOLVED).
    Two tier-A circulars from K-RERA had different content but were given the
    same sidecar filename because they shared a base document name. Each was
    reading the other's extracted text and serving wrong penalty figures.
    Fix: sidecar filenames now include a SHA1 hash suffix. Already applied.
    Do not revert to plain-name sidecars.

20. Filtering after retrieval causes silent widening (RESOLVED).
    An earlier design applied scope filters (domain, tier) after Chroma returned
    candidates. When the scope filter eliminated all candidates, the system fell
    back to unfiltered results. This meant a user asking a Karnataka-specific
    question could get answers from central regulations -- silently, with no
    indication the scope was ignored. The fix: all filters are now applied inside
    the Chroma where clause (pre-retrieval). test_scope.py section 6 explicitly
    asserts that the rejected silent-widening design fails so it cannot be
    reintroduced.
